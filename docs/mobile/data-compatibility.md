# Mobile data compatibility

The source baseline is the current `slax-reader-client` tree (commit `9951904405159f49f24effd4d42815f77ff33442` plus its production working-tree overlay). The new data layer uses PowerSync React Native 2.3.1 and OP-SQLite 18.2.5. The original schema, all 13 tables, previous-value tracking, and `schema_version: "2"` connection parameter are retained in `apps/mobile/src/data/schema.ts`.

## Runtime contract

The approved post-763 runtime contract separates presentation, verified data and network readiness. Create one `createMobileDataRuntime` at the app root. Once local logged-in state is known, present Login or the authenticated shell without waiting for refresh, sync or initialization. Account watchers and cached reads still await genuine ownership/migration admission; `verification-required` is a localized recovery state, not proof of sign-out or permission to read unverified data. Protected API/PDF calls await due main refresh, and PowerSync connects asynchronously only with valid account/origin-scoped credentials. Repository watchers return unsubscribe callbacks; every initializer and late publication is cancelled by runtime stop or account/origin replacement. Integrated native cold-start acceptance remains pending.

Unauthenticated startup must still clear prior-account data after verified database admission: absent credentials do not establish that synchronized rows, local-only JSON or cached articles are empty. Login may be presented while cleanup is pending, but new account activation/data access must not bypass `disconnectAndClear({clearLocal: true})`, article-cache and continue-reading cleanup. A cleanup failure remains localized and blocks unsafe account activation, rather than hiding the entire app or exposing previous-account data.

The daily main refresh policy is 86,400 seconds since the last successful refresh, not the signed token lifetime. Authorized live refresh at `https://reader-api.slax.dev` issued 1,296,000 seconds; the October 13 live `getSyncToken` observation issued 300 seconds (five minutes). The `powersync-token-24h` change sets new backend issuance to 86,399 seconds (24 hours minus one second) after deployment, and the mobile lifetime diagnostic expects that duration. The 24-hour cache ceiling remains separate: sync caching and SDK `expiresAt` must follow actual finite JWT `exp` with an appropriate safety window, never manufacture 24 hours of validity. Previously issued five-minute tokens remain usable until their signed expiration. PowerSync's UUID `sub` differs from the main API encoded ID; account/origin ownership cannot rely on those strings being equal. [Historical live contract evidence](evidence/2026-10-13-live-pdf-contract/verification.json) proves acquisition only, not deployment of the new lifetime, connection, synchronization or cold-start lifecycle correctness. The latest auth-review changes still require integrated verification.

Every account receives fresh repository, cache and UI preference objects bound to a permanently revocable database lease. Leaving an account revokes those objects synchronously, closes native Reader resource jobs, then clears data. Queued repository transactions recheck the lease inside the SDK transaction; an already running transaction rolls back if its scope is revoked before completion. Late watch callbacks are suppressed. Preference scopes share the original native CAS storage and global settings notification bus, but reject stale reads/writes and CAS retries. A previous Library focus callback cannot remove the next account's continue-reading value. Old objects never become active again when another account enters. Runtime keeps a private unscoped cache instance solely for administrative account cleanup.

Native Reader jobs additionally require a fresh opaque resource-owner identifier activated before the account objects are published. The UI forwards that owner to each Reader; a late-mounted previous-account view cannot acquire the current owner's native cache access. Runtime clears the exposed owner immediately on leave/stop and checks its lifecycle generation after awaiting native activation.

API requests capture an immutable session epoch synchronously before reading native preferences. The credential read and every transport attempt reject an expired epoch, so a delayed old-account POST cannot obtain the next account's bearer. Logout, login (including a fresh login with the same user/token), restoration and accepted refresh revoke earlier request scopes. Cleanup blocks credential acquisition; authenticated publication does not revoke requests started inside the same account's `enter` callback. Refresh commits and asynchronous 401 cleanup also check the original scope, protecting a fresh same-user session even if the backend issues an identical JWT. The synchronization connector retains that scope across cache reads, token requests and every preference CAS retry; an expired connection attempt returns no credentials and cannot update the current account's sync cache.

`SlaxApi` uses public `@slax-reader/contracts` exports where they match the mobile protocol. Mobile-only DTOs retain the actual Kotlin wire shape. In particular, mark profiles are `{uuid,nick_name,avatar}`, delete-account reasons are strings, and selected range offsets use `start_offset` in incoming reader data and `start`/`end` in stored `MarkPathItem` values. The shared marks input's `start_offet` typo must not be written to the mobile wire. API methods return the unwrapped envelope `data`; raw content and NDJSON AI streams use separate readers. Expo's fetch is used for native streaming. Request aborts remain attached until body consumption finishes. First-party reader metrics retain `/m` action headers; client events retain raw `/events` `{events}` bodies and device/client headers without requiring a response envelope.

After preference import and before session restoration or connector requests, startup selects the configured public beta origin only for `selected_env === 'BETA'`. `SlaxApi.setBaseUrl` validates and normalizes HTTP(S) origins; bearer requests cannot leave the active API origin. Debug environment changes persist for the next restart. Cached sync credentials additionally record `powersync_api_origin`; legacy credentials without that marker or credentials for another environment are refreshed before use, retaining the original token fields until a guarded replacement succeeds.

## Preferences and shared authentication

Credential rejection keeps the admitted local account available offline. Library exposes a native reauthentication route using the existing provider and agreement flow. Reauthentication accepts only the original account, leaves its database/cache owner and pending writes intact, and renews network/sync access after successful local acceptance. A different provider account is rejected without altering stored credentials. Native provider completion still needs its own acceptance evidence.

Sign-out persists `_slax_sign_out_pending_v1` before clearing account data. Protected requests and incoming shares refuse those credentials. After interruption, startup presents local sign-out state and completes cleanup before admitting another account; it cannot restore the old bearer as a usable session. Early preference failures and failed sign-out cleanup expose localized retry presentation. Runtime retries are coalesced and preserve the original migration files and recovery journal.

The original `user.preferences_pb` remains untouched. Android reads it from `Context.filesDir`; iOS reads it from `group.app.slax.reader`. The protobuf decoder follows the [AndroidX Preferences proto](https://github.com/androidx/androidx/blob/androidx-main/datastore/datastore-preferences-proto/src/main/proto/preferences.proto). Unsupported values or corrupt data stop migration and preserve the original file.

The new store is `slax.preferences.v1.json`, beside the original preference file. Its shape is `{revision:number, values:Record<string,string|number|boolean|string[]>}`. Native readers and writers serialize with `.slax-preferences.lock` (Android FileChannel lock, iOS POSIX flock) and perform revision compare-and-swap with an atomic file replacement. Migration imports every original key that has not already been written into the new store and commits `_slax_preferences_migration_v1` in the same write. It can safely retry after a process interruption or contention. A share extension must read the same store and lock; it must not keep writing the old DataStore after cutover.

Preserved keys include authentication/user identity, refresh time in **seconds**, PowerSync token/endpoint and refresh time in **milliseconds**, language, `cache_count` (including `-1` for unlimited), image download preference, detail alert preference, environment, continue-reading JSON (including collection owner/id), and stable analytics device ID. Tokens and preference file contents must never appear in logs or acceptance reports.

## Database ownership and upgrade barrier

`SlaxLegacy.beginDataOwnership` holds a cross-process `.slax-data-owner.lock` lease before inventory or database opening. It scans the actual application sandbox, returning every `powersync.db` outside the explicitly allocated new-owner directory. It does not open, copy, delete or alter legacy SQLite files. Inventory errors stop startup. The new database is created only when that complete inventory contains no legacy candidate.

An existing candidate requires `AdoptionEvidence` covering the precise discovered path, original Kotlin SDK 1.14.1, new React Native SDK 2.3.1, schema 2, a supported adoption path, and fixture checks for pending queue/order/boundaries, offline rows, local JSON and reconnect behavior. The two-platform immutable original-queue service, interruption and repeated-installation reports have been accepted as the technical basis for the constrained `slax-powersync-format14-schema2-v1` profile. `adoption-profile.ts` binds their four SHA-256 hashes, public SDK/core/driver versions and the native sources captured by the actual main builds. It derives per-install evidence only from one canonical native inventory candidate at the original Android/iOS database slot, with the current application/App Group lock identity. No runtime fixture marker, host report or device-specific path injection is trusted. The default runtime now derives this reviewed evidence while holding native ownership, retaining the complete pre/post SDK inspection and checkpoint gate. Current iOS native preference contention and normal-runtime startup passed without an explicit evidence override; the separate reports below record that execution. Unsupported or ambiguous inventories remain protected and cannot create an empty replacement database or become an ordinary signed-out session. Publisher signing and visible legacy-content QA remain separate acceptance work.

`openVerifiedDatabase` takes a complete native read-only snapshot while the exclusive owner lease is held. Both platform inspectors require the exact inventoried canonical path and use system SQLite read-only mode, without loading the new SDK. The verified profile currently requires internal format 14, SQLite user version 1, exactly the source's 13 storage tables, valid integrity, and SHA-256 checksums covering every raw ordered CRUD entry/transaction ID, offline row and local JSON row. Unknown tables or formats fail before the new SDK is opened. The `_slax_database_adoption_v1` preference checkpoint records opening/accepted/failed states before and after SDK initialization. The new owner is exposed only when all raw data and queue checksums/counts remain unchanged. Interrupted opening can retry only against the unchanged snapshot; a changed or failed checkpoint blocks automatic rollback. SDK initialization uses the public existing-file `dbFilename`/`dbLocation` path and preserves the original WAL/SHM family. Native inventory now also provides a logical owner namespace derived from the canonical App Group lock root and bundle identity, plus the exact application-relative database slot. Scoped checkpoints can follow a UUID container relocation only within the same native device/simulator prefix and slot. The current candidate, evidence path and canonical inspector check remain exact. An opening checkpoint still requires every raw checksum/count to match after rebasing only its recorded path. Backward checkpoints lacking native logical identity permit relocation only when the complete prior raw snapshot is unchanged, even if their phase was accepted; otherwise recovery remains protected. The derivation passed production-helper host execution and focused simulator SDK typecheck. The current Android bridge returned its exact owner/slot during native repeated-opening and process-fault tests. The current iOS bridge also returned its canonical owner/slot during a fresh original-queue first interruption and actual second-installation container relocation; that separate result is recorded below. The Android fresh first-adoption and actual repeated-installation counterparts are recorded separately below.

The complete old Kotlin SDK fixture, actual RN SDK/core host test and controlled Android/iOS same-identity OP-SQLite upgrades passed the supported existing-file path, documented with pinned official sources and reproducible programs in `apps/mobile/tests/data/adoption-fixtures/README.md`. Both native results cover synthetic upgrade preservation; the later isolated iOS real-service result is recorded separately below, while release-signed parity remains unverified. `tests/data/NativeAdoptionFixtureApp.tsx` is an explicit native development fixture entry guarded by `__DEV__`, the selected fixture flag, and a known synthetic original-producer marker checked before database access. Both genuine original Kotlin/DataStore producers measured core `0.5.1/d6c157e7` and published their markers only after the old owners closed. The replacement entries verified original AndroidX preferences/cache, queue values/boundaries, unchanged snapshot checksums, offline reopen and retry/upload order using native core `0.5.3/2ba6b280`. The iOS test permits preserved container relocation only inside the same controlled CoreSimulator and still requires the exact current native inventory path. If a platform's supported path fails, the required narrow legacy-native owner fallback remains implementation work; the constrained technical profile does not imply publisher or complete migration acceptance.

The [PowerSync transaction iterator](https://powersync-ja.github.io/powersync-js/common/interfaces/CommonPowerSyncDatabase#getcrudtransactions) is used instead of splitting operation batches. One upload invocation reads at most 100 transactions; it forms ordered batches targeting 20 operations while keeping a larger transaction whole. It pauses 200 ms between batches. A batch HTTP 400 retries each transaction individually; repeated isolated HTTP 400 completes only that rejected transaction. Any other error retains the failed and following transactions. Metadata tag/share diffs preserve the original fields and malformed JSON fallback. Completing transactions is always ordered because the SDK also completes earlier queued operations.

## Files and local reading data

Legacy article data is under Android `Context.dataDir` and iOS Application Support, not the new PowerSync database folder. Paths remain `bookmark/<key>/content.html` and `bookmark/<key>/images/<md5(normalized-url)>.<source-extension>`. Personal keys are bookmark IDs; collection keys are `collection-<ownerId>-<bookmarkId>`. Custom image schemes normalize `slaxstatics` to HTTPS and `slaxstatic` to HTTP before hashing. The original extension rule (last dot, trim query/ampersand, maximum ten lowercase characters, fallback `jpg`) is retained.

Local rows are read and updated as complete JSON in `ps_data_local__local_bookmark_info`. They retain `overview`, `key_takeaways`, `outline`, both reading positions, `mark_users`, download state, manual/automatic cache state and unknown future fields. An automatic download cannot demote a pinned manual article. File-cache cleanup does not mutate the CRUD queue. Debug cache maintenance uses `CacheMaintenance`: article HTML and images are measured/cleared only for rows whose `is_auto_cached` is explicitly zero, including collection-owner keys. Missing flags keep the source automatic-cache default. The Other category measures UTF-8 bytes and removes exactly `overview`, `key_takeaways`, `outline`, `outline_read_position`, `read_position`, and `mark_users` across all local rows, as the source does. Download state resets only after an article file is deleted. Empty manual rows are removed only when no unknown fields remain; unknown/pin metadata is retained. Category operations are serialized and update local JSON atomically without touching synchronized rows or pending CRUD.

Account-owned `BackgroundArticleCache` workers observe synchronized personal/collection rows, local state and cache preferences. They retain source success filtering/order, the default 50 articles or `-1` unlimited, independent collection-owner limits, three concurrent downloads per domain and queues capped at 100. Source image transports and optional image downloads are preserved. Manual articles and active foreground collection reads are protected from automatic eviction; collection failures wait for foreground retry. Removing obsolete automatic caches updates source-equivalent local state without touching synchronized data or pending CRUD. Account revocation cancels the workers before administrative cleanup. Native cache UI and background/device behavior remain acceptance work.
