## Over-the-air JavaScript updates (EAS Update)

Builds that embed `expo-updates` check the `production` channel at `https://u.expo.dev/<projectId>` on every cold start. Startup never waits for the check (`fallbackToCacheTimeout: 0`); a downloaded update applies on the next cold start, and a failed check keeps the embedded bundle or the last applied update. The runtime version is `<version>(<buildNumber>)`, so an update reaches only installed builds with the same `version` and `buildNumber`. Builds produced before `expo-updates` was added cannot receive updates. Fixture builds and builds generated with a non-production `EXPO_PUBLIC_SLAX_*` origin disable updates.

Publish only commits already merged into `dev`, and only when every commit between the installed build's commit (find it with `git log --first-parent -S '"buildNumber": <N>' origin/dev -- apps/mobile/package.json`) and the published commit changes JavaScript or bundled assets only. Anything that changes native code, generated projects, config plugins, `app.config.ts`, `eas.json`, mobile dependencies or the lockfile, or the local-data schema/migration modules (`src/data/schema.ts`, `upgrade.ts`, `adoption*.ts`, `installation.ts`, `legacy-preferences.ts`) needs a new native build with a new build number instead. Updates must stay within App Store and Google Play policy: fix bugs and adjust existing behavior, never change the app's primary purpose. An update contains the whole JavaScript bundle of the published commit; to ship one fix without later `dev` work, branch from the commit of the installed build, merge the fix into `dev` with a merge commit, and publish from the fix branch.

From a clean checkout of that commit, with the globally installed `eas-cli` logged in to the project owner account and no `EXPO_PUBLIC_*` variable set in the shell (production native builds must not override any `EXPO_PUBLIC_*` value either, or the update would not match them):

```sh
pnpm mobile -- update:publish --message "Fix ..." --rollout-percentage 10
```

The script publishes to the `production` channel with the EAS `production` environment and excludes local operator configuration and dotenv files, so the bundle uses the source production origins. Widen a staged rollout with `eas update:edit --rollout-percentage <N>`, stop one with `eas update:revert-update-rollout`, and roll back a completed update with `eas update:rollback` or `eas update:republish`. `eas update:insights` shows per-update launches, crashes and users. Usage counts against the EAS plan's update allowance (Free: 1,000 monthly active updating users and 100 GiB of bandwidth).
