# Isolated local StoreKit native acceptance

The preparation marker binds a closed set of the generated Xcode project, generated scheme and copied test Swift hashes. Admission revalidates all three before native result processing; an original-source-only preparation report cannot substitute for those generated inputs. After an actual build, bind the compiled scheme and final XCTest Mach-O to a separate build receipt and verify that receipt before claiming native execution. That build receipt and native execution remain pending.

This harness is prepared for `expo-mobile-migration` task 11.6. No native build, local calibration, adapter purchase, restore, cancellation, pending transaction or revocation has run yet. Passing the Node guards does not establish native purchase acceptance. The existing `expo-iap` 6.0.0 adapter and production `PaymentController` are used without another plugin.

## Isolation and admission

- Use a new, explicitly owned simulator marked `slax-controlled-local-storekit-simulator`, a unique run UUID and the application identifier `app.slax.reader.storekitfixture`. Existing migration/UI simulators, physical devices and Apple accounts are excluded.
- `prepare.mjs` first scans every artifact filename and file metadata. A GoogleService, credential, secret, private-key, `.env*`, `.dev.vars*`, signing-key or provisioning filename, symbolic link or irregular file stops preparation before any artifact content is read or copied.
- Only the retained public simulator Debug application `SlaxReader-ios-debug-identity-757-group-only.app` with launcher SHA `afca590846175cce828b550f5c92b17096b706c214de67ea1d6d1a380eebd97f` may be cloned. The test identity has empty public ad hoc entitlements, no Share extension and no production App Group. Every file-backed native section and complete Debug library remain equal to the retained artifact.
- The generated `.storekit` catalog contains only two run-specific `slax.local.fixture.<nonce>.monthly/probe` products. Its identifier and SHA, fixture source hashes, Xcode version, native artifact hashes and simulator owner are recorded. The scheme binds the real retained application copy as the tested application and includes the configuration in both Test and Launch actions. Generated project compilation and StoreKit synchronization remain unverified.
- `testNativeXcodeConfigurationPreflight` keeps the adapter application closed. Actual `SKTestSession` configuration mutation and native catalog loading must succeed before a synthetic calibration purchase. The returned native transaction must report the Xcode environment, exact test bundle ID and calibration product. It is finished and removed from the local test store. A bounded JSON attachment records only the completed public proof.
- `bind-preflight.mjs` accepts only one passing native calibration result on the allocated simulator and its unique nonfailure attachment. It rechecks the installed application, empty entitlements, missing Share, native section/library hashes, configuration/source hashes, exact current container, nonce and freshness before writing input/proof to that application's Documents. It never launches an application or purchases.
- The selected DEV application requires that exact request/proof before initializing the real adapter. Every native call and callback rechecks the immutable run; finished purchases must report `environmentIOS=Xcode` and the isolated `appBundleIdIOS`. Reported receipts/JWS and authentication values stay in process memory. The local verifier checks order/callback/finish plumbing and is not an Apple/backend receipt verdict.
- The fixture imports no normal application runtime, legacy bridge, API client, Firebase or telemetry sink. It uses synthetic in-memory preferences/session and no forwarded network request. The ordinary app entry remains unchanged unless the mutually exclusive `EXPO_PUBLIC_SLAX_STOREKIT_FIXTURE=1` DEV flag is selected.

## Prepared execution sequence

Execution requires an allocated native build/device slot and at least 4 GiB free disk, preferably 6 GiB. Estimated additional space is 2.5–3 GiB for one fresh simulator, the public native copy and the small control build. Do not create/boot it while another owned iOS simulator is active.

1. Create a fresh simulator and a canonical temporary `slax-native-local-storekit-*` owner directory. The marker must contain kind/version, exact device/name/runId, `applicationBundleIdentifier=app.slax.reader.storekitfixture`, `legacyApplicationAccess=false` and `productionTransactions=false`.
2. While that device is shutdown, run `node tests/payments-native/prepare.mjs --device <UUID> --owner-directory <canonical-owner> --artifact /tmp/slax-mobile-native-artifacts/SlaxReader-ios-debug-identity-757-group-only.app`. Preparation requires the reviewed Xcode 26.6+ line. It clones/generates files without compiling, installing, launching or purchasing.
3. Build only the small `StoreKitFixtureControl` scheme for that exact simulator. Verify the final tested product's Info.plist, empty ad hoc entitlements, native sections/library and signature after Xcode's packaging. Retained native code is copied, rather than recompiled. Preserve the real build command/log/products hash before running tests.
4. Boot only the allocated fresh simulator, install only that isolated product and run only `testNativeXcodeConfigurationPreflight`. Save the actual result bundle at `<project-directory>/native-preflight.xcresult`. Any configuration error, unexpected account prompt, missing product, wrong environment or bundle ID stops the attempt. Do not use a production/Sandbox fallback, modify StoreKit daemon storage or interact with an Apple-account prompt.
5. Run `node --experimental-strip-types tests/payments-native/bind-preflight.mjs --project-directory <canonical-project>`. This admits the actual completed proof, without launching or purchasing.
6. Start a separate development server with `EXPO_NO_DOTENV=1`, `EXPO_NO_TELEMETRY=1`, only `EXPO_PUBLIC_SLAX_STOREKIT_FIXTURE=1`, and a dedicated unused port. Attach the installed unique application to that server using its own `slax-local-storekit-fixture` development URL. Inspect any development onboarding first. Adapter buttons must appear only after the actual proof passes.
7. The prepared `testActualAdapterPurchaseAndRestore` activates only this already running guarded fixture, invokes its real purchase and restore buttons, waits for actual completion/state and active-entitlement counts, and retains native frames. Separately inspect the numeric JSON report and StoreKit transaction values before claiming any coverage. Pending/cancellation/revocation cases and final cleanup controls still need implementation/actual receipts after local configuration works.

Apple documents the local testing setup in [Setting up StoreKit Testing in Xcode](https://developer.apple.com/documentation/xcode/setting-up-storekit-testing-in-xcode) and [SKTestSession](https://developer.apple.com/documentation/storekittest/sktestsession). Apple DTS confirmed a configuration-sync issue for CLI tests and later reported a fix in Xcode 26.6; another developer still reported failure with the iOS 26.5 runtime. This is why configuration mutation and an actual Xcode transaction are prerequisites, even with the installed Xcode 26.6. [Apple Developer Forums discussion](https://developer.apple.com/forums/thread/826971)

## Scope that remains separate

Local `.storekit` transactions cannot prove App Store server JWS validation, publisher credentials, signed promotional offers, production order/account ownership or TestFlight processing. Native legacy preferences are not used by this payment harness. It does not change technical migration evidence, pending legacy queues or release acceptance. Original purchase cancellation, deferred/pending approval, restoration/revocation and error branches remain pending until actual controlled native receipts are collected.

Offline verification: `node --experimental-strip-types --test tests/payments-native/guards.test.ts tests/payments-native/prepare.test.mjs`, followed by `pnpm mobile -- typecheck` from the repository root.
