# Controlled PowerSync upgrade fixtures

These programs create synthetic data in a fresh fixture directory or isolated Android application sandbox. They never open a production installation or use real credentials. Generated databases, WAL files, binaries and Gradle output are ignored. Reports in `reports/` contain synthetic data and validation metadata only.

Current controlled Android first-upgrade evidence is recorded separately in `reports/android-original-queue-real-service.json`: the genuine original four operations plus new 5/6 survived opening-before-SDK and actual HTTP 503 process kills, then produced six PostgreSQL receipts, three real native SDK completions and matching materialized server/native rows, with default-stream and explicit WebSocket replication. Its initial package-absence assertion failed because an absent package returns exit one; the fresh owned AVD and first installation without replacement are recorded independently. The public-debug APK is development `1.0.0 (1)`, without publisher signing or a release `757` claim.

`reports/android-original-service-repeat-install.json` adds a real repeated same-artifact installation after new offline IDs 7/8, with native cross-process owner contention/SIGKILL, unchanged sandbox/database inodes, complete future JSON/preferences/cache and native logical identity. The strict completed actual-service report permits only the same Android run's repeat phases and is never converted into a fabricated adoption report. New 7/8 upload receipts use a synthetic callback; original-six actual-service evidence remains immutable and separate. All historical fixture sandboxes are preserved; neither report enables production adoption.

Its published Android Gradle, CocoaPod and Swift Package files pin core 0.5.3. See [published package metadata](https://registry.npmjs.org/@powersync/react-native/2.3.1) and the [SDK repository](https://github.com/powersync-ja/powersync-js).

## Host fixture

Use Node 22.22.3 or the repository-supported LTS version, Java 21 and Gradle 9.3.1. Root package dependencies must already be installed. The Kotlin producer downloads only public pinned fixture dependencies.

From the repository root, in a fresh generated directory:

```sh
SLAX_FIXTURE_ROOT="$PWD/apps/mobile/tests/data/adoption-fixtures"
gradle -p "$SLAX_FIXTURE_ROOT/kotlin-jvm" run --args="$SLAX_FIXTURE_ROOT/kotlin-jvm/generated" --console=plain
SLAX_FIXTURE_CORE_EXTENSION=/absolute/path/libpowersync-0.5.3.dylib node --experimental-strip-types "$SLAX_FIXTURE_ROOT/host/verify.mjs"
```

The extension must be the official macOS ARM64 [core 0.5.3 release asset](https://github.com/powersync-ja/powersync-sqlite-core/releases/tag/v0.5.3), SHA-256 `4fa96a98d7edb64a188493beb277bddcb7e85b286e2533d685ecf49ff51c6807`. The verifier checks that hash before loading it. Do not load an extension obtained from an unverified source.

The Kotlin host producer also creates `user.preferences_pb` with original AndroidX `PreferencesSerializer`/DataStore 1.2.1. The host verifier checks all 15 audited/synthetic-future fields and their types/units, interruption before commit, CAS contention with a concurrent setting, repeated import, and the original file's unchanged SHA-256. The JVM writer uses single-process `DataStoreFactory`; the Android fixture uses the original `MultiProcessDataStoreFactory`. This host result verifies the protobuf protocol and importer, not native locking.

The host verifier loads the real RN 2.3.1 database/queue classes and core 0.5.3 through the SDK's supported public `opened: DBAdapter` path. React Native platform hooks are stubbed and OP-SQLite throws if invoked. The adapter uses Node SQLite; this does not exercise OP-SQLite, native paths, native locking, or a device upgrade. The coordinator verifies the full read-only snapshot before and after initialization. Four old operations in two transactions, previous values, local hidden JSON, new offline operations with client IDs 5/6, close/reopen, retry retention, and ordered completion are checked.

A closed old SDK can leave recent transactions in `powersync.db-wal`. The host verifier clones **only its isolated synthetic fixture**, including existing WAL/SHM files. Production adoption opens the original path and preserves the entire SQLite database family; copying only the main file lost all pending operations in an early fixture experiment and is prohibited.

`host/InspectMain.swift` can be compiled together with `modules/slax-legacy/ios/DatabaseInspection.swift` and system SQLite for a macOS read-only comparison. Its checksum encoding matches the Android/Swift inspection modules. The saved Swift report is a macOS execution plus simulator typecheck, not an iOS device run.

## Android same-identity fixture

Use a freshly created, isolated AVD. Never use an existing personal device/AVD, erase its data, or install the fixture over a real application. Use Java 17, Android SDK 36 and the mobile project's Gradle 9.3.1 wrapper. The only signing material is the Expo-generated public debug test identity; no release signing files are used.

```sh
SLAX_FIXTURE_ROOT="$PWD/apps/mobile/tests/data/adoption-fixtures"
apps/mobile/android/gradlew -p "$SLAX_FIXTURE_ROOT/android-legacy" assembleDebug -PexpoMobileDir="$PWD/apps/mobile" --console=plain
adb -s "$SLAX_FIXTURE_DEVICE" install "$SLAX_FIXTURE_ROOT/android-legacy/build/outputs/apk/debug/slax-android-legacy-fixture-debug.apk"
adb -s "$SLAX_FIXTURE_DEVICE" shell am start -n com.slax.reader/.LegacyFixtureActivity
```

Wait for the fixture success text. It creates the exact old Android default database path, complete schema, four pending operations/two transactions, hidden local JSON, a cached article, and `files/user.preferences_pb` through original AndroidX DataStore 1.2.1 `MultiProcessDataStoreFactory`. All authentication values are fixed strings marked as invalid fixture credentials. The controlled marker is written only after successful creation.

Start Metro with `EXPO_PUBLIC_SLAX_ADOPTION_FIXTURE=1`; the application's development entry must select `tests/data/NativeAdoptionFixtureApp.tsx` only when `__DEV__` and that flag are both true. Build/install the Expo debug APK with `adb install -r`, retaining `com.slax.reader` and the same public debug signing identity. Do not uninstall between the old and new APKs.

The fixture component checks the marker **before inventory or database access**, requires the exact synthetic path/IDs/SDK, and then invokes the same native ownership lease, preference importer, read-only inspection, adoption coordinator and real native OP-SQLite SDK factory as the implementation. Missing or unfamiliar markers stop the test. The normal runtime receives no synthetic evidence; release mode rejects this entry. A successful run writes only validation metadata to `files/native-adoption-report.json`:

```sh
adb -s "$SLAX_FIXTURE_DEVICE" shell am start -n com.slax.reader/.MainActivity
adb -s "$SLAX_FIXTURE_DEVICE" shell run-as com.slax.reader cat files/native-adoption-report.json
```

The Android report intentionally leaves service reconnect, release-signed upgrade, and iOS false. The simulated retry/upload callback confirms queue order and completion; it does not contact a PowerSync service. Real service reconnect remains a separate acceptance test. Subsequent controlled process-kill results are recorded below; first-upgrade fault points remain pending. Do not enable a production adoption profile from this development marker or host report.

## Controlled process faults and owner contention

The selected development adoption entry also supports explicit synthetic control files. `tooling/native-fault-control.mjs` checks the original Kotlin marker before touching that namespace and accepts only a specified simulator UUID or emulator serial. Subsequent phases require the completed genuine native adoption report. First-upgrade phases instead require a fresh original producer with no completed report and the original four-operation/two-transaction queue. No phase clears application data, resets the database, enables a production profile, or installs an app automatically.

| Phase | Prerequisite and effect |
| --- | --- |
| `hold-before-first-sdk-open` | Fresh old producer; production coordinator commits opening checkpoint with original queue, then waits before new SDK initialization. |
| `resume-first-sdk-open` | After verified external SIGKILL; exact unchanged old snapshot and opening journal required, then the complete original-to-Expo adoption fixture runs. |
| `hold-before-sdk-open` | Completed adoption; production coordinator commits another opening checkpoint and waits before SDK initialization. |
| `resume-before-sdk-open` | After verified external SIGKILL; unchanged raw snapshot resumes through the production coordinator. |
| `hold-after-offline-commit` | Completed adoption and empty queue; one new synthetic two-operation transaction plus complete future local JSON commits, then waits. The fixed logical tag ID prevents duplicate reruns. |
| `resume-after-offline-commit` | Exact transaction IDs/client IDs/values/order, visible edit and full local JSON must reopen unchanged; simulated 503 retains the queue and ordered SDK completion consumes exactly two operations. |
| `hold-owner` | Holds the real native owner lease before database opening for an independent native process probe. |
| `repeat-accepted` | Reopens the accepted checkpoint through the production coordinator; it does not itself install an app. |

Build probes with `node apps/mobile/tests/data/adoption-fixtures/tooling/build-native-probes.mjs ios` or `android`. This creates a newly marked temporary output and prints its executable path without installing or launching anything. The Swift probe runs only under iOS Simulator, checks the exact requested simulator/App Group metadata/canonical lock path, and never creates the lock. The Android probe must run under the controlled package UID and uses the same native FileChannel lock primitive as the module. The controller marks only its freshly pushed probe archive read-only (`0444`), as Android 14 rejects writable DEX; all external commands have a 30-second bound. `host-identity` executes the actual production Swift logical-identity helper on host-only fixtures; it does not verify native bridge return values.

For an already allocated controlled device, write one requested phase and launch the selected development fixture through its dedicated Metro URL. For example:

```sh
SLAX_FIXTURE_CONTROL=apps/mobile/tests/data/adoption-fixtures/tooling/native-fault-control.mjs
node "$SLAX_FIXTURE_CONTROL" --platform ios --device "$SLAX_FIXTURE_SIMULATOR" --phase hold-before-sdk-open --run-id controlled-fault-run
xcrun simctl launch "$SLAX_FIXTURE_SIMULATOR" app.slax.reader
xcrun simctl openurl "$SLAX_FIXTURE_SIMULATOR" 'slaxreader://expo-development-client/?url=http%3A%2F%2F127.0.0.1%3A8084'
node "$SLAX_FIXTURE_CONTROL" --platform ios --device "$SLAX_FIXTURE_SIMULATOR" --status
node "$SLAX_FIXTURE_CONTROL" --platform ios --device "$SLAX_FIXTURE_SIMULATOR" --probe "$SLAX_FIXTURE_PROBE_EXECUTABLE"
node "$SLAX_FIXTURE_CONTROL" --platform ios --device "$SLAX_FIXTURE_SIMULATOR" --kill
node "$SLAX_FIXTURE_CONTROL" --platform ios --device "$SLAX_FIXTURE_SIMULATOR" --probe "$SLAX_FIXTURE_PROBE_EXECUTABLE"
node "$SLAX_FIXTURE_CONTROL" --platform ios --device "$SLAX_FIXTURE_SIMULATOR" --phase resume-before-sdk-open --run-id controlled-fault-run
```

The controller signals only one already-running exact installed Expo executable after matching a fresh request timestamp and a waiting synthetic state. It does not launch an app to discover a PID. Launch the next phase after the kill, or terminate a completed phase before writing the following request; keep the run ID consistent across each hold/resume pair. Do not change a holding phase's source through hot reload. Preserve the state/report before releasing the allocated device. The resume component closes the database and native owner in `finally`.
