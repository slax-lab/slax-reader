## 4. Follow-ups outside this change

- [ ] 4.1 Re-read the decision rule in `design.md` D1/D2 at the next gh-aw pin bump: the whitelist depends on *where* gh-aw compiles the pause, fork, draft and stack conditions, on the membership path reaching `activation` rather than `pre_activation`, and on the stale-lock check failing `activation`. A release that moves any of them can turn a real failure into a shape that reads like a decline (see the residual risk in `proposal.md`). This is a task rather than a comment because a pin bump is the only moment the question can be answered
- [ ] 4.2 Reconsider 1.5's declined-`/review` limitation if gh-aw ever accepts a trailing CRLF, or if `/review\r\n` is seen again in practice. The durable fix is upstream; the workflow-side alternative is to replace the `slash_command` trigger, which archive design D3 rejected once, so this stays closed until either the upstream matcher changes or the failure is observed to matter
- [ ] 4.3 Decide whether a passing skip may replace an existing failing verdict — found by round 3's review as a pre-existing hole this change neither introduces nor fixes. GitHub keeps the latest status per context and commit, so a `success` posted on the pull request head replaces a `failure` for the same context there. Any comment on a pull request — not only a `/review` one — produces a completed on-demand run whose stages are all skipped, and that lands in this change's `activation: skipped` passing branch, so a passer-by can clear a failing verdict on a head that has not moved since the review. That is archive task 7.13's intent ("a run that was not supposed to review must not touch the status") failing on the comment path, and it is unchanged from `main`: the same run posted the same passing skip under the old `agent: skipped` reading. The narrow question is whether a passing skip should be suppressed when a failing status already exists for the same context on the same commit — while keeping the requirement that a commit with no status at all still gets one, which is what makes a paused repository and a fork pull request mergeable
- [ ] 4.4 Stop the gate from failing on comments that are not about a pull request — also found by round 3's review, also pre-existing. The trigger list is not limited to pull requests, so a comment on a plain issue produces an on-demand run whose title carries the issue number; the gate's `gh api repos/$REPO/pulls/$PR_NUMBER` then 404s and `set -euo pipefail` aborts the step before it posts anything. Nothing is misreported (no status is written), but the gate workflow run fails on every issue comment in the repository. A `PR_HEAD` fetch that treats an unresolvable number as "not a pull request, leave the status untouched" would close it, in the same spirit as the routing guard this change leaves alone
