# Design

## Context

See `proposal.md` for motivation and scope. This worktree starts at `origin/dev@999dc2e5`; the earlier dirty checkout is not an implementation source.

- `apps/mobile/native/share/ios/ShareCollector.swift` awaits `URLSession.data(for:)` before inspecting status, although successful response data is unused. Its existing request/resource limits are 15 seconds. `ShareRequestDelegate` currently owns redirect rejection and metrics only.
- Android `ShareActivity.kt` already handles successful response status without consuming the body, but uses connect/read/write timeouts rather than a five-second total call deadline. Its activity owns the active OkHttp call and dismissal cancellation.
- `/v1/bookmark/exists` serves broader existing-client behavior. It may include trashed ordinary user relations, and Reader-link lookup excludes pending destinations. It is not a reliable save receipt.
- Ordinary add-URL persistence includes the bookmark and user relation before background crawl dispatch. Reader-fork admission also commits its destination relation before dispatch; parsing readiness must not gate a persistence receipt.
- Creation normalizes URLs through `processTargetUrl`; Twitter `/i/status/` is additionally resolved before persistence. Other supported short links, including Pocket Casts and Toutiao, are resolved after persistence and remain keyed by the original submitted URL.
- Native source copies are generated by `plugins/with-share.cjs`; Mobile version fields are owned by `apps/mobile/package.json`.

## Goals / Non-Goals

**Goals:** Keep one owner for each native request, give save acknowledgement a hard elapsed-time budget, and confirm persisted state with an additive read-only contract that does not depend on a response body. Preserve legacy lookup semantics and existing diagnostic contracts.

**Non-goals:** No request receipts table, alias registry, database migration, polling, automatic add-URL retries, main-app outbox changes, React Native API transport refactor, parser/workflow changes, or new dependency. This is a native incoming-share change, not browser-extension or outbound-share work.

## Decisions

### 1. A single bounded native state machine

Use the sequence `create -> success/error` or `create timeout -> confirm -> success/timeout`. A dismissal terminates either pending phase. The create budget is five seconds from dispatch; confirmation gets three further seconds, so the network portion is bounded to approximately eight seconds plus scheduler overhead. Input extraction, existing entrance animation, and success dismissal animation are outside that network budget.

Explicit non-success status is definitive for recovery eligibility. Error-body reading can use only the remaining create budget; if that body stalls, return the existing status-specific/default failure rather than converting an observed rejection into a recoverable ambiguous timeout. Offline/DNS/TLS failures retain existing behavior. Never dispatch a second application-level create request.

Alternatives rejected: reducing only connect/read idle timeouts does not establish a total budget; retrying add_url can cause additional work and is unnecessary for confirming the requested resource.

### 2. iOS success is decided at response headers

Extend the native transport boundary used by `ShareCollector` to inspect HTTP headers before success-body consumption. A task/delegate-backed operation can preserve redirect rejection and metrics while completing on 200/204 headers and cancelling the unneeded body transfer. Keep response-body parsing only for existing error behavior. The transport must have exactly one result owner across deadline, completion, and parent cancellation; an internally cancelled body after accepted headers must not overwrite accepted success with a cancellation failure.

Preserve `ShareViewController`'s existing task ownership, dismissal guards, success/error presentation, and input extraction. Do not hand-edit `ios/SlaxShare` copies. If a small transport source is extracted, update the config plugin source list and its existing fixture tests, not only the generated Xcode project.

On Android, retain the installed OkHttp transport and its status-first success behavior. Set an overall five-second call deadline and a separate three-second confirmation deadline, including response consumption. Classify the installed client's overall-timeout exception without conflating explicit activity cancellation. Reassign the activity-owned active call for confirmation, use a status-only receipt read, and avoid automatic recovery retries. If needed for executable host coverage, extract transport/orchestration from `ShareActivity` into a small app-owned class rather than expanding presentation responsibilities.

### 3. Add a bodyless, authenticated save-confirmation route

Add `POST /v1/bookmark/save_receipt` accepting the existing target-URL request shape. Return an empty `204` for confirmed saved state and an empty `404` when the resource is not confirmed, with `Cache-Control: private, no-store`. Authentication, validation, and infrastructure failures remain appropriate error responses; database failures must not be disguised as absence. Native callers accept only 204 as positive confirmation and need not parse any receipt body.

This avoids the original body-download failure in the fallback itself. A dedicated route is preferable to changing `/exists` or adding a mode that changes both its meaning and response format. Leave `BookmarkExistsResponse`, existing `/exists` consumers, and normal add_url responses unchanged. Register the controller through `pnpm api -- gen:all`; do not edit generated route or dependency files manually.

The repository query starts from `sr_user_bookmark`, constrains `user_id` and `deleted_at: null`, and joins matching bookmark identity and permitted private ownership (the current user or legacy public storage). It selects only existence, not article content. Do not filter processing status: a saved relation in pending, parsing, or failed state is still a saved bookmark. Do not infer success from a global bookmark row without the caller's active relation.

### 4. Reuse server-side creation identity without write side effects

For ordinary URLs, reuse scheme completion and `processTargetUrl` exactly; do not broaden host equivalence or strip arbitrary query parameters. Query the normalized submitted identity first, covering links persisted before workflow-side short-link resolution and the existing original-URL fallback when pre-save resolution failed.

For the concrete pre-save Twitter status-alias case only, use the existing read-only `needsResolve`/`resolveFinalUrl` path if the original identity was not found, normalize its resolved identity, and check it. The current `fetchTwitter` path has no explicit deadline: pass an optional cancellation signal through the resolver to its network/body read for receipt use, capped at two seconds of the three-second client confirmation budget. Existing creation/crawl callers retain their defaults. Do not call `tryResolveShortLink`, whose failure handling produces alerts; receipt failure must not launch workflows or alerts. A resolver failure remains unconfirmed/error and becomes timeout feedback on the client; no guessing authors, new alias state, or broad short-link crawl is introduced.

For Reader URLs, reuse `readerBookmarkUuid`, read-only source authorization, and existing destination-URL derivation (including PDF owner identity). Add a separate read-only destination receipt query that admits an active saved relation regardless of processing status. Do not call readiness-gated `destination()` or mutating admission/restoration helpers. Keep normal Reader lookup and fork behavior unchanged.

### 5. Preserve current diagnostic schema and evidence

Keep the existing single start/terminal lifecycle and sanitized field vocabulary. The creation operation retains ownership of the existing `net`, `error`, `http`, and request-duration evidence; do not reuse its metrics/listener object for confirmation. A recovered invocation has final outcome/reason success while retaining the original timeout error and create metrics. The existing total duration includes confirmation. Do not introduce per-retry events, new log schema, full URLs, response bodies, or a blocking diagnostic flush. Extend existing diagnostic tests to ensure recovered success and dismissal still produce one terminal event and preserve redaction.

### 6. Version metadata follows the explicit increment approval

During implementation update `apps/mobile/package.json` from `1.0.27 / 799 / 798` to `1.0.28 / 800 / 799` for `version / buildNumber / previousBuildNumber`. The previous value is a source-build bound, not claimed store history. Generate native metadata through the existing Expo/config-plugin commands and verify iOS main/share marketing and build versions, Android versionName/versionCode, and runtime display/runtime-version metadata. Update the current source-version statement in `docs/mobile/release.md`; preserve historical release receipts.

A build-number increment can trigger the existing EAS production build/auto-submit workflow after a qualifying merge into dev. Creating this local worktree and preparing or applying this change does not itself authorize pushing, merging, signing, uploading, or publication.

## Risks / Trade-offs

- A healthy save can take more than five seconds to persist -> one negative receipt is only unconfirmed state at query time. Keep the requested timeout outcome and do not automatically retry or claim permanent absence.
- Both create and receipt response headers can be delayed -> three-second receipt deadline bounds the UI; recovery is best effort, not an offline-delivery guarantee.
- Twitter alias resolution introduces a second third-party read in that existing pre-save rewrite case -> use the same read-only resolver with a receipt-only cancellation budget; do not resolve unrelated short links. Failure remains unconfirmed.
- Reader source access can be revoked after a destination was saved -> retain current source-authorization semantics and return unconfirmed rather than bypass access rules.
- Early iOS body cancellation changes completion ordering -> exercise header-before-body stalls, deadline races, and user cancellation through the actual native transport and preserve accepted terminal state.
- Existing mobile parity and diagnostic changes are still active -> this delta owns only the new recovery contract; preserve their shared contracts and avoid duplicate capability deltas.

## Migration Plan

No data migration is required. Deliver the additive API route before releasing native clients that depend on it. An older API's missing route results in the bounded timeout outcome, never false success or a create retry; the header-only creation improvement remains useful. Rollback the native change independently, and retain the additive receipt route while any distributed client may use it. Do not deploy as part of this planning task.

The owner's final acceptance decision is automated verification for this logic-only change: run the relevant API controller/domain unit tests, real Swift/Kotlin transport host tests, diagnostic/plugin/version tests, API typecheck, and iOS/Android JavaScript bundle validation. The controlled HTTP cases reproduce a withheld create acknowledgement and a stalled success body, checking exact request counts, timing, cancellation, and recovery outcomes; API tests separately cover persisted-state predicates, normalization, owner isolation, and trash/pending states. No new native build, device matrix, or manual UI acceptance is required for this PR because presentation is unchanged and the owner explicitly chose unit tests for the conditional failure scenario. Preserve earlier failures and gaps in `validation.md`; do not describe host tests as device or full API-to-native end-to-end acceptance. Commit, push, and PR creation are authorized after these final checks pass; merging and deployment remain separate.
