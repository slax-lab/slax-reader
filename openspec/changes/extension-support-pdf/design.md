# Design

## Context

See `proposal.md` for motivation and scope. Relevant observed behavior:

- `apps/extension/src/entrypoints/background/browserService.ts` gates collection on HTTP(S) content-script readiness and returns without visible fallback after its bounded readiness wait. `background/index.ts` funnels toolbar, Alt+Y, and page context-menu actions through that service, but toolbar/menu login checks currently happen before dispatch.
- `src/components/Collect.vue` calls the HTML bookmark endpoint with `src/utils/website.ts`'s cloned `outerHTML`. The internal PDF viewer must not be scraped, but its outer source document can host injected UI. `RecordBookmark` assumes `sender.tab` is the source tab; a new extension-page sender would violate that assumption.
- `wxt.config.ts` has an action without `default_popup`, Chrome minimum 115, Slax host permissions, and `tabs`, `storage`, `cookies`, `webRequest`, and `offscreen` permissions. Content scripts match `<all_urls>`. There is no existing user-visible extension page suitable for this flow.
- `src/bridge/request.ts` is the current request adapter, using `src/utils/session.ts`'s cookie-backed session and device/client/locale headers. The legacy `src/utils/request.ts` is not the integration point.
- `POST /v1/bookmark/add_url` accepts `{ target_url }` and returns `{ bmId: '' }` after acceptance, not a bookmark UID or completed capture. Backend PDF recognition uses response MIME/signature, not suffixes.
- `apps/api/src/domain/bookmark.ts:696` enforces `labService.assertEnabled('pdf')` before reading an upload. Uploads use a raw body and a `filename` query, deduplicate by per-user content hash, and return a positive numeric encoded `bookmark_id` and a nonempty `bookmark_uid`; the corrected response also includes an optional authoritative title. `packages/contracts/src/pdf.ts` supplies `PDF_MAX_BYTES` (50 MiB).
- `apps/web/app/components/BookmarkList/AddUrlTopModal.vue` demonstrates the correct raw `File` plus `Content-Type: application/pdf` transport. `packages/frontend-utils/src/request.ts` preserves `File` bodies but JSON-serializes other bodies; its `uploadFile` helper labels a raw file as multipart and is not appropriate here.
- `add-pdf-bookmarks/specs/pdf-bookmarks/spec.md` owns existing acquisition, Labs, privacy, and reader requirements. No living PDF capability appears in `openspec list --specs` yet. This change adds the extension-facing capability and amends the existing PDF delta in place for title resolution, without adding a competing capability delta.

## Goals / Non-Goals

**Goals:** Keep action identity, file bytes, credentials, and server status separate; preserve the existing HTML fast path; make local-file permission and recoverable failures understandable; produce tests against the shipped WXT entrypoint rather than an unrelated demo.

**Non-Goals:** No generic background fetch proxy, binary runtime-message serialization, service-worker file transport assumption, source-cookie harvesting, Web styling migration, a different PDF parser, breaking backend contract changes, or modification of independent Labs settings visibility.

## Decisions

### 1. One dispatcher, with a collector-first HTTP route

Capture the initiating tab ID and its current URL before any asynchronous login, readiness, or focus change. Remove only the premature PDF-path login exits from toolbar/menu dispatch; preserve normal HTML login behavior. For HTTP(S), retain the bounded collector readiness handshake. If a live HTML collector exists, use it even for a `.pdf` suffix. If the restored controller identifies PDF, inject the compact collection overlay and automatically submit the original URL there. If injection is refused, show refresh/retry guidance without submitting an unclassified HTTP source. PDF-looking URLs may inform neutral explanatory copy but must not bypass a working collector or trigger Labs rejection. This deliberately supports extensionless viewers without guessing browser-private viewer DOM structure or requiring a broad new network observer.

Local `file:` source tabs use the extension document embedded in their in-page overlay, never to the server URL endpoint or HTML collector. Local bytes, not suffix/MIME alone, determine PDF validity. Reject unsupported `chrome:`, `edge:`, other extensions, `data:`, and `blob:` sources with visible feedback. Do not extract arbitrary URLs from a viewer's query string; standard built-in viewers must be verified to expose the original HTTP(S)/file URL via the initiating tab. The existing context menu remains a page-context action where the browser exposes it; do not add a Chrome-150-only `tab` context.

Alternative rejected: always branch on `.pdf` or scrape viewer HTML. Both miss extensionless PDFs and misclassify HTML. An unavailable HTTP collector alone is not evidence of PDF: recover injection or show an injection failure instead of silently submitting a different collection flow.

### 2. Inject the existing collection overlay on the original page

The human explicitly rejected both a full save tab and a separate popup window. Chrome's built-in PDF viewer has an outer source document where content scripts can run; isolation of the internal viewer does not prohibit adding an overlay to the outer document. Remove the `application/pdf` early return. The source content script mounts the existing `slax-reader-modal` Shadow DOM host and a compact extension-document iframe displaying `CollectFeedback.vue`. Keep the HTML collector unchanged and omit the article sidebar on PDF surfaces. The iframe preserves privileged cookie/file APIs while keeping all visible feedback on the initiating PDF page.

Readiness probes explicitly distinguish `html` from `pdf`. For an already-open tab without a live controller, inject the existing content-script bundle on the user action using `scripting` and `activeTab`, then probe again. Do not classify HTTP documents by `.pdf` suffix. Add only the required `scripting` permission and web-accessible `pdf-save.html` resource; its private APIs remain gated by a live, pinned operation and bound frame, not public resource availability.

The inline iframe first identifies itself through extension messaging. Its source controller rejects synthetic DOM events and verifies the exact iframe `contentWindow`, extension origin, and operation ID before confirming its frame ID and a temporary pairing token through isolated extension messaging. The background validates that confirmation comes from the source tab's top content frame. Only the confirmed extension frame can claim, read or submit the operation. A website-created sibling cannot gain authority by copying an operation ID from the DOM. Tokens are cleared after binding and never persist beyond trusted session metadata.

On mount, check source and authentication, then automatically submit the online URL or read/upload the permitted local PDF. There is no second Save click. Show the existing loading/success treatment and close inline success feedback after two seconds, matching normal collection. Errors and recovery remain visible. Resize/close messages update only the operation's bound source overlay. Neither normal save feedback nor retry creates a new browser window or save tab.

When file URL access is disabled, Chrome also blocks content-script injection into the local source. Configure a per-tab toolbar action bubble before the user clicks, with the real screenshot and localized steps. The reserved `_execute_action` command preserves Alt+Y through the same browser action on Chrome 115+, rather than depending on the newer general `openPopup` API. A best-effort `openPopup` call handles races on browsers where it exists; no window fallback is allowed. The bubble's no-tab extension-document sender is authenticated separately from the in-page iframe. Enabling the switch may reload the extension: return to the original PDF and invoke the action again. This is the sole permission-driven presentation exception; permitted files and online PDFs use the injected overlay. If injection fails on another restricted source, the action bubble explains refresh/retry and does not silently submit that HTTP URL.

Preserve the current collection renderer's light palette as the local exception in `DESIGN.md`, with labelled controls, status announcements, focus visibility, narrow widths, long filenames and reduced motion. Do not import Web tokens, scrape the internal viewer, replace the viewer, or change the offscreen bridge.

### 3. Resolve original local-file bytes in the extension document

The direct-file path is a required acceptance gate, not a promise that service-worker `fetch(file:)` works. After human planning review, the first implementation spike must load the actual WXT page in isolated Chrome profiles and establish a browser-supported extension-document transport (for example XMLHttpRequest with `responseType = 'blob'` if verified). Test the generated manifest's effective `file:///*` access, adding only that narrowly scoped host declaration if required; `<all_urls>` content matching alone is not assumed to authorize file reads.

Check `browser.extension.isAllowedFileSchemeAccess()` before direct reads and recheck on retry. The browser's “Allow access to file URLs” toggle is user-managed; `permissions.request()` cannot turn it on. Offer browser-appropriate extension-details instructions/link and explain before navigation that permission changes may close the page and clear session state. After a reload, return to the original PDF and invoke toolbar/Alt+Y again; retry is available only while context survives. The permission popup contains a real settings screenshot and numbered instructions. There is no picker alternative in this direct-save flow.

Read only the source pinned by the dispatcher, with timeouts, cancellation and measured size limits. Prevent retained/unbounded allocation beyond the accepted file budget; reject excessive advertised size where available and abort when observed bytes exceed `PDF_MAX_BYTES`. Verify the chosen transport can enforce this during the spike rather than buffering arbitrary files first. Accept nonempty files at most 50 MiB and check for `%PDF-` within the first 1024 bytes, matching the existing server rule. Signature validation is not a complete PDF parser: later corruption/password/extraction errors stay governed by the existing backend/reader. Use a safe decoded basename (including spaces/non-ASCII), remove separators/control characters, cap to the server filename policy, and use `document.pdf` as fallback. Strip viewer fragments from local read targets; retain the original source identity for navigation validation.

If no supported direct transport satisfies these constraints on a target browser, stop and report a blocking feasibility result for human review. Do not silently ship a picker-only substitute, disable browser security, add a native helper, or raise the minimum browser version.

### 4. Use existing request/auth contracts precisely

Online: call `POST /v1/bookmark/add_url` with only `{ target_url: originalUrl }`, preserving query parameters and not replacing the URL with a viewer/extension URL. Send no viewer DOM, source-site cookies, or local binary data. Acceptance with an empty `bmId` becomes “Submitted; processing” and an action to open the bookmark list, never an invented detail link or processing-complete badge. Existing backend/list state remains authoritative for eventual success/failure. Server-side public retrieval cannot access login-protected downloads; explain that limitation and explain that a downloaded file can be opened in Chrome and saved through the same local flow, without credential copying or automatic privileged remote fetch.

Local: wrap the verified Blob as a `File` in the extension document and use `src/bridge/request.ts`'s `request.post` with the fixed upload path, basename query, raw File body, and `Content-Type: application/pdf`. Do not call `uploadFile`, use FormData, JSON/base64-encode bytes, or change shared helpers. Require a nonempty `bookmark_uid` and a positive numeric encoded `bookmark_id` in the successful payload, then offer the existing `/b/<bookmark_uid>` reader route. Saved bytes do not mean AI extraction is finished.

Reuse the current cookie session and client headers immediately before a request. Missing/expired sessions lead to the existing login flow with an explicit retry in the surviving source overlay, not stored tokens or automatic replay. Clear in-memory file data on logout/account switch and require a new explicit attempt; never continue an operation into another account without confirmation.

### 5. Preserve Labs gating, including the hidden-setting consequence

For direct file upload, load existing read-only `GET /v1/user/labs` and expose the upload control only when `pdf.enabled` is known true. Missing, disabled, or unavailable state must not be treated as enabled; show disabled or retryable-unavailable feedback and do not read/upload the local file. Backend `LAB_FEATURE_DISABLED` remains authoritative if state changes after the check.

For online URLs, do not apply PDF gating based on suffix or an unavailable collector. Submit through the existing URL path and let response detection and the backend enforce acquisition policy; report synchronous errors and make clear that queued saves may later fail. Existing PDFs remain readable under existing access rules.

The parallel settings-visibility work hides the PDF toggle without removing the server gate. Consequently users without existing opt-in cannot acquire PDFs through this extension; a settings link is guidance only, not a promise that an enable control exists. Show a truthful unavailable-for-account message when blocked, never auto-enable, expose a replacement enable toggle, or bypass the server. Availability for new users requires a separate human-approved product/gating change outside this proposal.

### 6. Bind operations and privileged messages to trusted sources

Store only bounded, short-lived operation metadata in trusted-context `storage.session`: random ID, source tab ID/navigation identity, source URL needed for retry, surface kind and bound frame ID, state, creation/expiry, and result IDs where present. Proposed bounds are at most 20 operations and a 15-minute expiry; enforce pruning on creation/read plus tab-close cleanup. Local URLs are sensitive operational metadata: never put them in page URLs, durable/local/sync storage, analytics, API bodies, request headers, or logs. No binary or auth tokens enter operation storage.

Serialize get-or-create per source navigation before opening UI so rapid toolbar/shortcut/menu actions focus the same operation and cause at most one active submission. Persist the metadata needed to reconcile a worker restart; do not depend solely on worker global variables. If a page/request is lost, mark interrupted and require explicit retry instead of background replay. Clear bytes after terminal outcomes, cancellation, or expiry.

New page messages carry operation IDs, not caller-chosen fetch URLs or source tab IDs. Check `sender.id`, exact parsed extension scheme/host and the allowed built page pathname, its bound source tab/frame identity, and operation validity. A content script shares the extension ID but is not an authorized acquisition iframe. Use URL parsing compatible with Chrome 115, not substring matching or an unconditional newer Origin API. Reject spoofed, stale, mismatched, missing, or external senders. Expose only the iframe document as web-accessible, while requiring trusted source-controller pairing before privileged messages and reject direct entry with an unknown operation ID. API destinations are fixed to configured Slax endpoints.

Revalidate the source tab/navigation before acquisition and before submission. If the source changes or closes before submission, stop with source-changed feedback; focusing another tab alone does not change the source. Once submitted, retain the immutable source association and do not apply results to a different navigation. Cancellation aborts the local read/request where possible but must disclose that a server-accepted save may still finish; it does not promise rollback. Notify bookmark synchronization through a dedicated validated completion path: do not pass the embedded save document into existing `RecordBookmark` logic as though it were an injected source collector. Readiness may identify the outer PDF source controller, but must distinguish it from an HTML collector and never mark the embedded extension document ready.

## Risks / Trade-offs

- [Local transport, file access, and built-in viewer URL exposure differ by browser/version] → Make the real-browser direct-file spike a blocking prerequisite; record browser versions, generated manifest shape, permission toggle behavior, and bounded-read evidence. No security-disabling launch flags or mocked transport count as proof.
- [MV3 restarts, rapid clicks, and focus changes can misroute or duplicate work] → Source pinning, serialized operation creation, session metadata, explicit retry, and restart/navigation tests. Backend upload hash deduplication complements but does not replace client exclusion.
- [URL submission has no result UID and may fail later] → Report queued status only, link to the list, and verify eventual readable PDF with a real test backend separately from mocked transport tests.
- [Labs switches may be hidden for disabled users] → Preserve the gate and state the account limitation; do not mark universal availability or fix the unrelated settings surface here.
- [Read/upload errors may include local paths or signed queries] → Map to safe error categories; never log raw source URLs, transport errors, binary bodies, cookies, or tokens from this flow.
- [The direct read duplicates browser viewer access and uses bounded memory] → Read only on the explicit save operation, bound bytes/time, release on cancellation/expiry, and avoid binary messaging/storage.
- [Fixture-only browser coverage could mask real integration failures] → Maintain distinct unit, real-browser mocked-API, and real-backend acceptance evidence. The human reported completing manual end-to-end verification on 2026-10-15; the fixture remains separate automated regression evidence.

## Migration Plan

No database or backend migration is required. After human review, implement in this worktree, run the existing repository commands, inspect the built MV3 manifest/page and zip, then test unpacked Chrome with disposable profiles and explicit test configuration. Update `apps/extension/README.md` and existing extension documentation with file permission, privacy, Labs, and protected-download limitations. No `CHROMEWEBSTORE.md` currently exists; this is not store-release authorization or a reason to invent release metadata.

Rollback consists of reverting the extension dispatcher/page/permission changes together, preserving existing HTML collection and backend PDF bookmarks. Expired session operation records must be harmless. The human authorized commits, pushes, and a pull request on feat/extension-support-pdf. Store publication and deployment remain separate operations. Before any later behavior-changing push, run all three `REVIEW.md` passes (Bugs, Security, Compliance against `extension-support-pdf`) and resolve Important findings.

### Confirmed-upload and title correction (2026-10-14)

The backend Hashid encoder returns a number. Validate this existing numeric upload contract instead of rejecting successful responses as strings. Once a valid response is received, it is authoritative for that request's saved result; subsequent operation completion/synchronization errors must not replace it with uncertain-request feedback. Pending requests still revalidate source/account identity and remain cancellable.

For local files, lazily load the repository's existing unpdf 1.8.1 parser in the extension document and parse only metadata, with evaluation disabled, a short timeout, cancellation and parser cleanup. Keep the raw immutable File and its basename for upload. Resolve the display title through the shared XMP dc:title → document-info Title normalization rule, then the basename without .pdf. Parser failures retain the filename fallback and do not block otherwise valid PDF bytes. Do not scrape the built-in viewer or trust website-provided titles.

The backend stores original bytes before metadata parsing takes ownership of its input buffer. For a new upload, resolve metadata before completing the stored bookmark with pending text status, return its actual saved title, and schedule full text extraction asynchronously as before. Preserve duplicate-content behavior and user alias titles. The optional response title lets updated clients display the authoritative title while remaining compatible with older deployed servers. This implements the existing add-pdf-bookmarks metadata requirement; do not create a competing pdf-bookmarks delta spec. Backend deployment requires a separate explicit instruction.

An explicit repeat upload of identical bytes also repairs a legacy filename-derived stored title when embedded metadata is available, without replacing the original file, resetting extraction state, or touching the user alias. No bulk backfill is performed.

### Online metadata-empty documents (2026-10-15)

The supplied arXiv document has an empty Info Title and empty XMP title. Its selectable first-page title spans two 16.18-point horizontal lines, above approximately 10-point body text. A larger rotated arXiv identifier is not a document heading. Extend the existing backend parser with a bounded geometry-based fallback: normalize page rotation with the PDF.js viewport, exclude vertical text and boilerplate, require a heading to be larger than the dominant body text and in the upper page, and join only adjacent aligned lines of comparable size. Ambiguous/single-style/scanned pages retain the existing filename fallback. Metadata remains authoritative. Never infer authors from the heading or perform OCR/AI/network enrichment.

Resolve this fallback during both backend metadata/title resolution and full text extraction, with existing parser cleanup/timeouts. Reuse first-page text already read during full extraction. Cache-hit capture must read only the stored immutable file and refresh the title without refetching the URL or replacing original bytes, text status or alias titles. No bulk backfill or deployment is authorized. The pdf-bookmarks delta remains owned by add-pdf-bookmarks and is revised there, rather than duplicated by this change.
