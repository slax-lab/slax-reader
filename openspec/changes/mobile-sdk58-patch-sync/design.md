# Design

## Context

See proposal.md for motivation and scope. Mobile declares Expo SDK modules with a mix of exact pins (`expo`, `react-native`, `@expo/ui`, `expo-hinge`) and tilde ranges. The committed native projects are generator-owned: `apps/mobile/ios/Podfile.lock` records exact React Native and Expo pod versions, and the Android project resolves module versions from `node_modules` at build time. `docs/mobile/release.md` forbids publishing an OTA update across a change to mobile dependencies or the lockfile, because the runtime version is `<version>(<buildNumber>)` and an update would reach installed binaries built from the old native code.

## Goals / Non-Goals

**Goals:**
- Match the SDK 58 recommendation exactly, so `expo install --check` reports no mismatch.
- Produce every tracked output through its generator and confirm both native platforms build and cold-start.

**Non-Goals:**
- No source or behavior change in app code or native modules; the only config plugin change is the Android ABI list.
- No dependency outside the SDK 58 recommendation.

## Decisions

- **Edit the manifest to the published SDK table instead of running `expo install --fix`.** `--fix` rewrites manifest entries to its own range style, which would turn the deliberate exact pins into ranges. Editing each entry to the `expo@58.0.23` `bundledNativeModules.json` value keeps the existing pin style; `expo install --check` then proves the result matches the SDK.
- **Keep React at 19.3.0.** React Native ships a renderer built for one React version; SDK 58 pins 19.3.0 for React Native 0.88.x, and 19.3.1 would fail the renderer version check at startup.
- **Regenerate native outputs instead of hand-editing them.** Run `pnpm mobile -- pods` for `Podfile.lock`. Compare `pnpm mobile -- prebuild` output before and after the upgrade on the same worktree, so drift caused by the absent local operator configuration is not attributed to the upgrade.
- **Own the Android ABI list in the existing config plugin.** `android/gradle.properties` is regenerated by prebuild, so a hand edit would be lost. `with-native-compatibility.cjs` already owns other Gradle properties through `withGradleProperties`; setting `reactNativeArchitectures` there keeps one owner and adds no dependency. The React Native Gradle plugin turns this property into `ndk.abiFilters`, which filters both compiled and prebuilt native libraries. An Expo build-properties plugin or an EAS-only environment override were rejected: the first adds a dependency for one property, and the second would make local release builds differ from store builds.
- **Keep `armeabi-v7a` with `arm64-v8a`.** Some x86 Chromebooks translate only 32-bit ARM code, so an arm64-only build would not run on them.
- **Deliver through a native build, not OTA.** The change alters native code, so installed `1.0.28 (802)` binaries must not receive it as an update. It ships as `1.0.29 (803)`.

## Risks / Trade-offs

- [Native behavior regression from React Native 0.88.1 or Expo Modules Core 58.0.30] → Build Android Debug and iOS Debug from the upgraded tree and cold-start both to the first screen; run the existing mobile checks, tests, bundles and native-resource checks.
- [An OTA update published from a later `dev` commit reaching 802 binaries] → The release document already forbids it; the pull request states that this change needs a new native build.
- [Upstream fixes that cannot be reproduced locally, such as a truncated OTA asset in an EAS production build] → Record them as upstream fixes that were not reproduced, instead of claiming local verification.
- [x86 ChromeOS devices run through ARM translation, with lower performance and higher battery use] → Accepted by the owner; both ARM ABIs remain so translation is available on all Android-capable Chromebooks.
- [Developers on an x86 emulator lose the default native libraries] → Pass `-PreactNativeArchitectures=x86_64` for that local build; the committed default stays ARM-only.
- [Local build environment differs from EAS cloud builds] → Local builds use the committed unconfigured project without operator configuration; EAS production signing, Firebase configuration and store delivery are verified only by the release pipeline.
