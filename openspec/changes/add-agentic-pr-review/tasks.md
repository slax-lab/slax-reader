## 7. Findings from the first real review (PR #18)

The review workflow's first run reviewed its own implementation pull request and reported two Important findings plus three Nits. They are tracked here because they are all still actionable:

- [x] 7.1 Fix the gate so a run producing no verdict cannot pass silently — attempted by overriding the custom job's `if:`, which the compiler merely **ANDs** with its own output-types gate (verified in the compiled lock file), so the verdict job alone cannot be the gate; the companion workflow from design D4 is required instead
- [ ] 7.2 Implement the companion gate workflow (design D4) — `pr-review-gate.yml` is `workflow_run`-triggered and always reports one status; **reopened** because the first verification showed it posts to the wrong commit for `/review` runs (task 7.11)
- [x] 7.3 Drop `cancel-in-progress` from both review workflows: a cancelled run is not a passing required check, so superseding a run must not happen
- [x] 7.4 Skip draft pull requests (`github.event.pull_request.draft == false`) so a pull request is not reviewed twice; verified in the compiled condition
- [x] 7.5 Gate the paused-notice companion on the commenter's repository role — implemented, then **reopened** because it declared only `pull-requests: write` while `gh pr comment` needs `issues: write` (task 7.12 fixed the permission and confirmed the reply on #23), and closed again on review feedback that the task list still carried a resolved blocker
- [x] 7.6 Reconcile the spec's trigger list with the implementation: `reopened` is now specified, and draft pull requests are excluded by requirement
- [ ] 7.7 Correct the PR body so it names the single required check the companion reports; task 5.2 has been updated
- [ ] 7.8 Finish suppressing framework issues: the first real review run still opened `[aw] Failed jobs: PR Review` (#19, closed) — and the compiled lock shows `GH_AW_REPORT_FAILED_JOBS: "true"` and `GH_AW_REPORT_INCOMPLETE_CREATE_ISSUE: "true"` despite `report-failure-as-issue: false` and `report-failed-jobs: false`, so those frontmatter switches did not take effect in v0.88.7; find the correct knob (or override the env vars) and re-verify with a failing run
- [x] 7.9 Decide how a push after a review is handled — decided: accept and document. The status is attached to the reviewed commit and re-review is an explicit `/review` (documented in `REVIEW.md` → Automated review). A `synchronize`-triggered carry-forward was rejected: it would report a verdict for a commit nobody reviewed
- [x] 7.10 Verify the companion gate empirically — done after merge (it cannot run pre-merge: `workflow_run` only triggers workflows on the default branch): clean review → `success — Reviewed: no Important findings`; paused/skip → `success — Review skipped (paused, fork pull request, or budget cap)`; `/review` → status on the pull request head, not `main`; the gate's success satisfies the required check (`gh pr checks` shows `pass`); after a push the new head has no status and the pull request stays blocked (task 7.9 by design); the failure path → probe #29 reported one Important Compliance finding (a `packages/**` change with no `OpenSpec:` line) and the gate reported `failure — Review reported Important findings` on the reviewed commit. Still unexercised: a fork pull request (task 4.2)
- [ ] 7.11 Fix the gate's target commit for on-demand runs (found by the second review): `workflow_run.head_sha` is the pull request head only for the `pull_request`-triggered workflow; the on-demand one runs from the default branch, so its run head is main's tip and `workflow_run.pull_requests` is empty — implemented by giving both review workflows a `run-name` containing `#<pr>` and having the gate resolve the pull request head from the run's display title, falling back to the payload SHA
- [x] 7.12 Give the paused-notice companion `issues: write` (found by the second review): `gh pr comment` posts to the issues comments endpoint, so `pull-requests: write` alone fails with "Resource not accessible by integration" and the paused reply never appears; confirm empirically in task 5.4 — confirmed there: the notice was posted twice on #23 by `github-actions[bot]`
- [x] 7.13 Gate bypass 1 — a skipped run must not clear a failing verdict (found by the third review): the gate now reports only for runs that were supposed to review — the automatic workflow on a `pull_request` event, the on-demand one on a comment event — and leaves the status untouched otherwise, so the on-demand wrapper's `pull_request: [opened, edited, reopened]` trigger can no longer launder a failing verdict (routing verified by simulation)
- [x] 7.14 Gate bypass 2 — report against the reviewed commit, not the current head (found by the third review): `pull_request` runs now use the run's own `head_sha` (which *is* the reviewed commit) and only comment-triggered runs resolve the pull request head
- [x] 7.15 Gate bypass 3 — success must require that a review was actually published (found by the third review): a green result now additionally requires a review authored by `github-actions` with `commit_id` equal to the reported SHA, otherwise the gate fails closed with "No review published for this commit"
- [x] 7.16 Decide the fate of the framework issues the review runs keep opening — decided and implemented: `.github/workflows/agentic-noise-cleanup.yml` closes bot-created `[aw] ` issues carrying the `agentic-workflows` label, with a comment pointing at the failing run, because the frontmatter cannot suppress the failed-job path in v0.88.7 (tasks 1.8/7.8)
- [x] 7.17 Fix the reported commit for automatic runs (found by the fourth review): `pull_request` runs are checked out as the merge commit (`refs/pull/N/merge`) while a published review is pinned to the pull request head, so comparing the two made the "was a review published" guard fail closed on every clean review. The gate now reports on the `commit_id` of the review this run published, falls back to the pull request head when the run published none, and still requires a published review for a green result

## 8. Follow-ups found while operating the review

- [x] 8.1 Stop the review agent from reaching for GitHub over the network (found in the review of #24, whose published body carried a "Firewall blocked 1 domain: `api.github.com`" warning): the agent had run `curl https://api.github.com/repos/…/actions/runs?per_page=2` to check the routing claim beside it, and the AWF firewall denied the request by design. Fixed by adding the `actions` toolset to `tools.github` — the read the agent wanted now exists as a tool — plus a prompt section stating that the sandbox has no GitHub network route, so `gh`, `curl` and `git fetch` cannot work. Verified with an accidental A/B: #28's own reviews (which change `.github/workflows/**`, so they are exactly the CI-touching case) carry no firewall warning with the fix in the run, while probe #29, whose run used `main`'s config, still carries "Firewall blocked 1 domain". The review of #28 also caught a second-order defect in the same task's prompt text — the first version of step 1 replaced one dead end (`git diff` against a base branch that need not exist) with a worse one (`git diff HEAD^`, which is the pull request's previous commit because gh-aw checks out the head branch, not the merge commit), so the wording now names the GitHub tools as the reliable source and requires an explicitly resolved range, checked against the tools' file list, with an instruction to report a partial diff rather than silently review one. Round 3 then corrected that correction with measurements of its own, which is worth keeping: the checkout is the **head branch on the comment path and the merge commit on the automatic path** (so `git diff HEAD^` is the last commit in one case and the base tip in the other), and gh-aw **restores `.github/`, `.agents/` and `AGENTS.md` from the base branch**, so a workflow or rulesync file read from the worktree is the base version even when the pull request changes it — the prompt now states both and sends workflow-file reads to the tools. (Corollary for operating this review: prompt *body* changes reach the agent only after merge, while *frontmatter* changes apply immediately to `pull_request` runs, whose lock file comes from the pull request.)
- [ ] 8.2 Make the paused reply say *what* is paused (found by a human reading the Feishu notification produced by the paused drill in task 5.4): "评审已暂停" was read as *human* review being paused, because nothing in the notice named the subject. The notice, `REVIEW.md` and the notification card now name the automated review, say the pause is deliberate, and state that human review is unaffected; the notice also carries a marker so the notification bridge recognises it exactly instead of matching the word "paused" (implemented in `slax-notify-bridge` PR #2, merged and deployed).
