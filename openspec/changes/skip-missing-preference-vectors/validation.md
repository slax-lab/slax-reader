## Incremental maintenance: implemented behavior

On 2026-11-09 the human replaced the D1 conditional-write design with one SQLite-backed Durable Object per user. The unmerged D1 table, its 00066 migration, store and integration test were removed; they were never deployed. `VectorPreferenceObject` (Core) stores per-article weight, Collection membership and an 8-byte fingerprint, plus float64 raw, centered and owner sums, the mean version, carried clusters and a sequence. An in-memory queue runs one batch at a time and combines calls that arrive during a batch; no alarm, lease, pending table or conditional write exists. The article Workflow now runs `article-write` (which also returns the previous representative vector when it replaced or deleted one), `article-visible`, and `preference`, which applies and verifies in one retried step. A batch reads weight and membership with one PostgreSQL query and current vectors with one batched read, subtracts the contribution identified by fingerprint, adds the current one, commits locally and publishes the user preference and owner Collections. Absent state, another mean version, or a fingerprint matching neither available vector rebuilds from `listCollectionMembers` and `listUserArticles` and recomputes clusters; incremental batches keep clusters and drop a cluster whose medoid left. Refresh routes rebuild through the object and publish only their own target: the Collection route publishes only that Collection and the article-preference route only the user preference. A Collection refresh now reads all of the owner's own readable article vectors, not only starred members, because the owner and user aggregates share one state.

## Incremental maintenance: known limitations

- The private configuration needs the `VECTOR_V5_PREFERENCE` Durable Object binding and a new, unused migration tag with `new_sqlite_classes = ["VectorPreferenceObject"]`; the deployment check fails without them. slax-lab/slax-reader-config#11 adds both, tagged `vector-preference-v1`, to all four files; each passes this repository's `checkDeployment`, and `api/dev.toml` fails it without the change. Configuration takes effect at the next API deployment. Wrangler refuses a binding to a class the deployed code does not export, so a `hotfix/*` API deployment to `beta` or `main` before this change is promoted there would fail. The local `deploy/local/api.toml` is gitignored and was not changed, so local Workflow runs need the same addition.
- The main checkout's local D1 had applied the removed 00066 migration; its `slax_vector_preference_state` table and `d1_migrations` record were deleted on 2026-11-09 and both counts verified as zero. Remote D1 never received it.
- Interest clusters do not reflect new saves until the next rebuild. Nothing reads them while the article feed is paused.
- Moderation outcomes recorded without a later article event are not applied to the owner aggregate until the owner's next Collection refresh or bulk refresh.
- If an event fails after its article write and before its apply, the next event for that article rebuilds the user once; until then other events publish sums that still count the article's earlier vector.
