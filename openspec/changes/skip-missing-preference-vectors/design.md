# Design

## Decisions

- User article preference accounting counts every eligible row. An absent by-ID result increments `missing` and contributes nothing; only valid present vectors contribute to raw sums, centered sums and cluster input. The subscribed-Collection preference applies the same accounting. Collection representation aggregation keeps its strict missing-dependency behavior.
- Attach optional numeric coverage to VectorRefreshResult for user preferences. Keep publication state written for a valid partial result; callers can distinguish coverage from native write visibility. The CLI validates and preserves only the three safe numeric counters.
- A nonempty eligible set with zero used vectors throws no_usable_preference_vectors before the stale-profile deletion branch. This preserves old profiles. An empty eligible set still deletes them.
- Do not catch vector reads or normalization errors as absence. No intermediate profile is written; raw, centered and cluster calculations complete before the final existing upsert.
- The partial-coverage fix preserves request routes, algorithms, Collection representations and all source-file behavior. The incremental section below owns the Workflow and storage changes. No recovery platform or cloud mutation is part of implementation verification.

## Incremental maintenance

- One SQLite-backed Durable Object, `VectorPreferenceObject`, exists per user, addressed with `idFromName(userId)`. Core hosts the class; Edge reaches it through the `VECTOR_V5_PREFERENCE` binding with `script_name`, like the existing Core objects. It is a plain per-user queue: no alarm, lease, pending table or version-conditional write. Different users have different objects and never wait for each other.
- The object stores one `preference_entry` row per eligible article: bookmark ID, applied weight, Collection membership flag and an 8-byte fingerprint of the applied stored vector (empty while the vector is missing). One `preference_state` row holds float64 raw, centered and owner Collection sums, the `EMBEDDING_MEAN_VERSION` they were built with, the carried interest clusters and a state sequence. Article vectors themselves are not copied into the object.
- Requests interleave inside a Durable Object while it awaits PostgreSQL or Vectorize, so an in-memory queue runs one batch at a time. Calls that arrive during a batch join the next one, so a sync touching many articles of one user collapses into a few batches. A batch takes at most 100 articles.
- An article event writes the article vector as before. When that write replaced or deleted an existing representative vector, the step result also carries the previous representative values. The next step calls the object's `apply`, then verifies the published records; a failed or not-yet-visible check throws, and the step retry applies again. Applying again is harmless because a matching fingerprint yields no change, and it republishes the current sums.
- A batch reads current weight and membership for its articles with one PostgreSQL query and their current vectors with one batched read. For each article it identifies the applied contribution by fingerprint: the current vector, or the handed-over previous vector. It subtracts that contribution, adds the current one, and commits entries and sums in one local transaction with sequence `max(previous + 1, now)`. A cluster whose medoid left the preference is dropped. The batch then publishes the user preference and every owner Collection, carrying `state_version` in their metadata.
- The object rebuilds from current rows and existing vectors when it has no state, when its mean version differs, when an applied fingerprint matches neither available vector (the vector was replaced outside the event path, or an event failed between its article write and its apply), or when a full refresh asks for it. A rebuild pages the user's eligible articles with weight and membership, reads their vectors, recomputes interest clusters from the recent action window, and replaces the stored state. It never calls Jina.
- Interest clusters are recomputed only by a rebuild. An incremental batch keeps the stored clusters, so a new save does not read the recent action window.
- The owner aggregate uses the existing published-member rule with weight 1 and raw sums only. It is published to every Collection of the owner; a closed Collection or an owner with no members has its record deleted. A member whose vector is missing fails publication with `missing_dependency` and the state persists, so a later event completes it.
- A Collection event refreshes the owner's starred articles as before, then rebuilds the owner's object, which applies account share settings. The article preference refresh route and the Collection refresh route rebuild through the same object; the subscribed-Collection preference keeps its full recomputation outside the object.
- Visibility accepts the written token or a strictly newer published `state_version`. If two batches' writes become visible in reverse order, the older Workflow's check fails, and its retry republishes the current sums.
- When a user has no eligible article left, the batch deletes the preference records and clears the object's storage.

## Trade-offs

Partial preferences intentionally omit unavailable contributions and can change when those vectors become available; coverage makes this visible. All-missing preferences remain explicitly incomplete rather than deleting last-known output. Operational failures still fail the target so a service outage cannot silently erase most history.

Incremental maintenance adds a Durable Object class, its binding and a migration tag that operators add to their private configuration. Storage is a few dozen bytes per eligible article plus about 40 KB per user. Each article event makes one Durable Object call; the object is active only for its PostgreSQL and Vectorize calls, while the Workflow waits for visibility. Floating-point residue from repeated deltas stays far below published precision, and any rebuild resets it. A 64-bit fingerprint collision between an article's old and replacement vectors would hide the replacement until the next rebuild; the probability per comparison is about 2^-64. Interest clusters do not reflect new saves until the next rebuild; nothing reads them while the article feed is paused, and restarting the feed should add a scheduled rebuild or online clustering. Moderation outcomes recorded without a later article event are not applied to the owner aggregate until that owner's next Collection refresh or bulk refresh.
