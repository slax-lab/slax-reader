# Design

## Decisions

- Extend the existing aggregate helper with optional coverage accounting supplied only by refreshUser. Without that argument, its strict Collection behavior remains unchanged. Count all enumerated rows, increment missing for absent by-ID results and continue; only valid present vectors contribute to sums and the existing visit callback.
- Attach optional numeric coverage to VectorRefreshResult for user preferences. Keep publication state written for a valid partial result; callers can distinguish coverage from native write visibility. The CLI validates and preserves only the three safe numeric counters.
- A nonempty eligible set with zero used vectors throws no_usable_preference_vectors before the stale-profile deletion branch. This preserves old profiles. An empty eligible set still deletes them.
- Do not catch vector reads or normalization errors as absence. No intermediate profile is written; raw, centered and cluster calculations complete before the final existing upsert.
- Preserve request routes, Workflow sequencing, algorithms, Collection representations and all source-file behavior. No recovery platform, extra storage or cloud mutation is part of implementation verification.

## Incremental maintenance

- State lives in one D1 row per target in `slax_vector_preference_state`: `u:<user>:article` for the user article preference and `o:<owner>:collection` for the owner Collection aggregate. A row holds float64 raw and centered sums, a packed ledger sorted by bookmark ID with the applied weight and a 64-bit fingerprint of the applied stored vector (empty while pending), the `EMBEDDING_MEAN_VERSION` it was built with, and a version. Versions are `max(previous + 1, now)`, so a target that is deleted and recreated never reuses an older version. Empty targets delete their row. A ledger over 120,000 entries exceeds the 2 MB row limit and is not persisted, so such a target falls back to rebuilding on each event.
- An article event runs retire, article write, apply. Retire subtracts the ledger's contribution and marks it pending while the old vector still exists, which keeps deletions and re-embeds incremental. Apply reads the current eligibility weight with a single-row PostgreSQL query and the current stored vector, then corrects the sums by the difference against the ledger. Every state change is a conditional write on the read version; a conflict re-reads and retries with jittered backoff. If the article write or its visibility check fails after retries, a restore step re-applies the article from its current stored vector before the Workflow fails, so an embedding failure never drops a previously counted article.
- Apply rebuilds from current rows when state is absent, built with another mean version, or when the ledger fingerprint no longer matches the stored vector because it was replaced outside the event path. Each attempt rebuilds at most once; if its conditional insert loses a race it continues incrementally against the winner, since the ledger delta stays correct for any state. The existing full refresh routes use the same rebuild and persist it, which makes them the backfill and repair path.
- After applying, the event publishes only if its state is still the newest. An older event stands down and its result is marked superseded. Published records carry `state_version`; visibility accepts the written token or a strictly newer published version, so concurrent events no longer fail their own visibility checks. If the vector index applied an older upsert after a newer one, the profile stays stale until the next event, as concurrent full recomputes already could; no lock or lease is added.
- The owner aggregate uses the existing published-member rule with weight 1 and raw sums only. It is published to every Collection of the owner, so owners with several Collections compute once. A pending or absent member still fails publication with `missing_dependency`, but the state persists so a later event can complete it.
- Interest clusters are still computed at publish time by full Ward clustering over at most 2,000 recent actions, reading only articles whose ledger entry has a vector. This is the remaining per-event history read and is left to the online clustering change.

## Trade-offs

Partial preferences intentionally omit unavailable contributions and can change when those vectors become available; coverage makes this visible. All-missing preferences remain explicitly incomplete rather than deleting last-known output. Operational failures still fail the target so a service outage cannot silently erase most history.

Incremental maintenance trades a D1 row per active target and more write-path logic for per-event cost that no longer grows with history. Floating-point residue from repeated deltas stays far below published precision, and any rebuild resets it. Eligibility changes that dispatch no article event, specifically the account-level snapshot-sharing setting and moderation outcomes recorded without a later article event, are not applied to the owner aggregate until that owner's next Collection refresh or bulk refresh; the per-event full recompute used to absorb them.
