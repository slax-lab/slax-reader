# Proposal

## Why

Slax Reader has no macOS application that combines an offline library and reader with native window, menu, and system behavior. Add a macOS-only desktop client with a Rust-owned data plane so untrusted saved content cannot acquire application credentials or network privileges.

## What Changes

- Add `apps/desktop` with a Cargo workspace, Tauri 2.12.4 shell, independent `slax-core`, and Vue 3/Vite/Pinia/vue-i18n presentation, as specified in sections 1–8 of the supplied plan; expose commands through `pnpm desktop -- <command>`.
- Provide an overlay title bar, system traffic lights and sidebar material, native menus/context menus, hide-on-close/Dock reopening, system appearance, reduced-transparency behavior, and English/Chinese UI. Add a separate Desktop profile to `DESIGN.md` and generated engineering rules from `.rulesync/` during implementation.
- Implement Rust-only HTTP, credential storage, account-isolated PowerSync/cache ownership, typed IPC and cancellable Channel subscriptions. Port existing Mobile upload, permission, token, cache, and PDF validation behavior with explicit desktop lifecycle differences.
- Deliver the library, sandboxed HTML/PDF reading, annotations/comments/replies/tags, reading position, AI overview/outline, gallery, sharing, offline downloads, RSS, settings, feedback, account deletion, subscription entry, capture entry points, and menu bar status.
- Precede shared-reader consumption with a separate, behavior-preserving `packages/reader-embed` extraction PR. Keep the Mobile host adapter and its generated bytes stable; keep desktop-specific protocol/CSP changes outside that extraction.
- Record installed native window behavior (B) and sandbox/reader/PDF transport evidence (C). PowerSync remediation and the original proof A are excluded because the user has already fixed that work; integrate the working result without repeating its repair or validation. Add macOS CI and release tooling for universal builds and dev/beta/main channels, with distribution activation subject to deferred decisions.

## Capabilities

### New Capabilities

- `desktop-shell`: Native macOS window, appearance, menus, accessibility, and lifecycle.
- `desktop-data-core`: Rust transport/storage authority, account isolation, IPC, synchronization, and query publication.
- `desktop-reader`: Isolated HTML/PDF rendering, selection, annotations, AI, media, and reading progress.
- `desktop-offline`: Account-scoped article/image/PDF downloads, validation, scheduling, and recovery.
- `desktop-integrations`: Capture, RSS, settings, account actions, subscriptions, telemetry, and menu bar integration.
- `desktop-delivery`: Root commands, macOS checks, native acceptance evidence, universal packaging, and staged delivery.

### Modified Capabilities

None. Existing Web/Extension/Mobile profiles, Labs gates, authentication providers, release promotion rules, and in-flight capability ownership remain authoritative.

## Impact

New application and shared reader package; root package/tooling/lockfiles; `DESIGN.md`; `.rulesync/` and its generated files; macOS CI/release workflows; Mobile reader resource/build/test paths. Rust dependencies include the user-provided working PowerSync integration (pin the consumed version/revision), reqwest/rustls, security-framework, and macOS system adapters. Login depends on the separate `desktop-login-handoff` change; this change does not add its API or Web routes.

The user's section 9 is deferred: do not ratify its defaults or implement the standalone sync-error-status fix. Earlier repeated requirements remain proposals under sections 1–8; the minimum macOS version and final distribution activation remain open. The source's unavailable “first inventory” is replaced by an explicit scope matrix in the design; unlisted product additions require review. Native Share Extension, optional metered-network pause, and dark article reading remain out of scope. Planning readiness does not establish completed implementation or passing B/C validation. PowerSync fixes, SDK fork/patch/upstream PR work, and the original proof A are excluded by the user's follow-up; ordinary desktop integration remains in scope.
